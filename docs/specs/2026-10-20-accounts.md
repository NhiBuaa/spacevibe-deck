# Accounts: Google sign-in and tiers

- **Started:** 2026-10-20
- **Status:** Draft. The owner took decisions 1–4 on 2026-10-20. This spec waits for approval
  before implementation.
- **Baseline:** `main` at `f74328ff`.
- **Surfaces:** a new account service in Electron main, the renderer (account label and a
  Settings → Account page), a migration under [`backend/supabase/`](../../backend/supabase/), and
  the privacy notice. This spec leaves the analytics Worker and the landing's feedback sign-in
  untouched.

## Goal

A Deck user can sign in with Google and see the tier their account is on. Signing in is
optional. Signed out, every feature works exactly as it does today and Deck reads "No account".
Deck is free and open source, so there is no billing. The paid tier exists as a value on the
server that nobody holds yet. A future mobile app signs into this same account.

## Decisions (owner, 2026-10-20)

1. **Scope is identity plus tier.** Settings sync and feedback attribution wait for later.
2. **Google sign-in, through Supabase Auth.**
3. **Reuse Deck's Supabase project** (`calkpkscykzmvyayfxih`), the one behind feedback. Account
   tables live beside the feedback tables, each table with its own RLS.
4. **No charging.** "Paid" is a plan value on the server. This slice gates nothing in the app by
   tier.

## Decisions taken in this spec (approved with it)

- **D1. Loopback callback.** Sign-in redirects to
  `http://127.0.0.1:<ephemeral port>/auth/callback` with PKCE, following RFC 8252 §7.3 for native
  apps. A `deck://` URL scheme was turned down because it is a bundle-config fork. It needs
  electron-builder `protocols`, registry entries on unsigned Windows builds, registration in dev
  runs and second-instance argv handling, and Deck has none of these today.
- **D2. `@supabase/supabase-js`, in the main process only.** Hand-written `fetch` against GoTrue
  was turned down. It is smaller, but PKCE exchange and token refresh are security code that the
  official client already maintains. The mobile app will also use this SDK against the same
  tables. The Electron framework dominates installer size, so the extra bytes do not matter.
- **D3. Two tiers: `free` and `pro`.** A missing or unknown value reads as `free`.
- **D4. Two Google sign-in paths coexist on purpose.**
  - **Landing feedback** keeps Google Identity Services, verified by the Worker
    ([2026-10-08 spec](2026-10-08-feedback-sign-in-status-mail.md), decision 2).
  - **The app** uses Supabase Auth.
  - **Merging them later is a join, not a migration.** Both paths can share Deck's Google OAuth
    web client, and Google gives one account the same `sub` across clients. So a merge joins on
    `auth.identities.provider_id`. The merge itself is out of scope.
- **D5. No remote avatar.** The renderer shows the account's initial and email. Deck makes no
  image request to Google and the renderer gains no new network origin.

## Requirements

### Signed out

- **A1. Optional.** No feature, menu action or setting requires an account. Deck never prompts
  the user to sign in, at launch or anywhere else.
- **A2. "No account".**
  - **Label:** signed out, a persistent surface reads "No account". Activating it opens Settings →
    Account.
  - **Placement:** chosen from 2–3 gallery specimens that the owner approves by eye.
  - **Settings → Account** always exists.
- **A3. Zero network.** Signed out, Deck sends no request to Supabase or Google. The supabase-js
  client is built lazily, only when a stored session exists or a sign-in starts, so no request
  can come from simply creating it.

### Sign in

- **A4. Flow.** "Sign in with Google" runs these steps in main:
  1. Start a one-shot HTTP listener on `127.0.0.1`, port 0.
  2. Ask supabase-js for the Google authorize URL (PKCE, `redirectTo` = the listener's
     callback, `skipBrowserRedirect`).
  3. Open that URL in the system browser with `shell.openExternal`.
  4. Accept only `GET /auth/callback`, and exchange its `code` exactly once.
  5. Reply with a static English page: "Signed in. You can close this tab and return to Deck."
  6. Close the listener.
- **A5. One bounded flow.**
  - **Second click:** while a flow is open, another click reopens the browser on the same flow.
  - **Listener closes** on success, on Cancel, on error, or after 5 minutes. The UI then returns
    to signed out with a short reason.
  - **No port stays bound** once the flow has ended.
- **A6. Errors.** Deck returns to signed out with a one-line reason and does not retry when:
  - the callback carries a provider error (`error`, `error_description`);
  - the code exchange fails;
  - the machine is offline.

### Session

- **A7. Tokens stay in main.** The access and refresh tokens exist only in the main process.
  The renderer receives a display state and never a token. The state is one of `signed-out`,
  `signing-in`, or `signed-in` with `{ email, name, plan }`.
- **A8. Encrypted at rest.**
  - **Storage:** the session persists in `userData/account.json`, encrypted with Electron
    `safeStorage`.
  - **Encryption unavailable:** the session stays in memory only, and the user signs in again
    on the next launch. It is never written in plaintext.
- **A9. Unreadable file.** A file Deck cannot read or decrypt counts as signed out.
  - **Never written defaults:** nothing overwrites it, matching the write-lock trap.
  - **Replaced only by a sign-in:** it differs from the stores under that trap because it holds
    only a credential that cannot be recovered. So the next successful sign-in replaces it.
  - **Sign out** deletes it.
- **A10. Refresh.** Tokens refresh in main, through supabase-js `autoRefreshToken` with a
  storage adapter backed by A8.
  - **Server rejects the refresh** (session revoked or expired): Deck signs out.
  - **Network failure:** Deck keeps the cached signed-in state and lets the client retry on its
    own schedule.
- **A11. Sign out.** Deck clears the local session first. It then revokes this session's
  refresh token on the server, best effort. Offline, sign-out still completes locally.
- **A12. Every window agrees.** Main owns the state and broadcasts each change to every window
  in one event.

### Tier

- **A13. The server owns the plan.** The migration creates
  `public.profiles (id uuid primary key references auth.users on delete cascade, plan text not null default 'free' check (plan in ('free', 'pro')), created_at timestamptz not null default now())`.
  - **Row creation:** a trigger on `auth.users` insert creates the row.
  - **Trigger safety:** it is `security definer` with a fixed `search_path`.
  - **No desktop columns:** the mobile app reads the same row.
- **A14. RLS.**
  - **RLS is enabled.**
  - **Own row only:** `authenticated` may `select` only its own row (`id = auth.uid()`).
  - **No writes:** there are no insert, update or delete policies for `anon` or `authenticated`,
    and the matching table privileges are revoked.
  - **Plan changes** are an owner action in Studio.
  - **Trigger function:** `EXECUTE` is revoked from `public, anon, authenticated`, the same as
    the two feedback trigger functions.
  - **Feedback tables:** their existing deny-all stays unchanged.
- **A15. Reading the plan.**
  - **When:** main reads `plan` after sign-in, and once per launch while signed in.
  - **Cache:** the last value stays in the session file, so an offline launch still shows it.
  - **Fetch failure:** Deck shows the cached value, or `free` when there is none.
- **A16. No gating.** Deck displays the plan and gates nothing on it.

### Privacy, security, docs

- **A17. Public key only.** The app ships the project URL and the publishable (anon) key as
  constants in one main-process config module.
  - **Test override:** that module accepts an override for the URL and key in unpackaged builds
    only, so tests can point it at a stub.
  - **Service-role key:** it never enters the app or the repo.
  - **This is the project's first public key.** Shipping it in a public repo and an extractable
    asar lets anyone call PostgREST as `anon`, and as `authenticated` after signing in, for the
    whole project, feedback included. On 2026-10-20 the existing objects already deny both
    roles: `feedback_reports` revokes all from `anon, authenticated`, and both trigger functions
    in [`20261008000100_feedback.sql`](../../backend/supabase/migrations/20261008000100_feedback.sql)
    revoke `EXECUTE`. Every new object follows the same rule.
- **A18. Telemetry unchanged.** No account ID, email or plan enters the analytics payload, and
  the payload snapshot test passes without edits. Crash reports carry no account fields:
  `sendDefaultPii: false` stays and nothing calls `Sentry.setUser`.
- **A19. IPC.**
  - **Channels:** four new flat channels, `account_state`, `account_sign_in`,
    `account_cancel_sign_in` and `account_sign_out`.
  - **Event:** one new event, `account:state-changed`.
  - **Contract test:** all five are added to `scripts/electron-ipc-contract.test.ts` (R6).
  - **Renderer access:** through a new `src/host/account-host.ts` (R8).
- **A20. Privacy notice.** A new dated notice under `marketing/public/privacy/<date>/` covers:
  - Google sign-in is optional, and signed-out use sends nothing;
  - what is stored: email, name, Google account ID, plan and sign-in timestamps;
  - Supabase is the processor and Google the identity provider;
  - how to erase an account: ask the owner, who erases it in Studio.

  `/privacy` points at the new notice and earlier notices stay. The in-app Privacy section
  mentions the account.
- **A21. Docs.**
  - **[`backend/README.md`](../../backend/README.md)** gains an Accounts section: the migration,
    Google provider setup, the redirect allow-list, changing a plan, and erasure.
  - **`docs/internals/`** gets one paragraph or page on why the session is owned by main and
    why tokens never cross IPC.
  - **`docs/user/`** gets a short "Sign in" entry.

## Acceptance criteria

- **Signed out, no requests:** a counting `fetch` injected into the account service records zero
  calls from launch to quit (A3).
- **Sign-in against a stubbed GoTrue** (unit tests with fake timers and an injected
  `openExternal`):
  - a callback with a code ends signed in, with the email and `free`;
  - a callback with a provider error ends signed out, with a reason;
  - Cancel closes the listener, and so does the 5-minute timeout.
- **No token in the renderer:** a contract test pins the state payload's shape (A7).
- **Storage edge cases:**
  - `safeStorage` unavailable: nothing is written;
  - corrupt `account.json`: Deck reads signed out and leaves the file untouched until the next
    sign-in.
- **RLS, by a pgTAP test under `backend/supabase/tests/`:**
  - a user reads only their own `profiles` row;
  - a user cannot update `plan`;
  - `anon` reads nothing;
  - an authenticated user cannot read `feedback_reports` and cannot execute any `public`
    function.

  The test runs on the local stack (`supabase start`, then `supabase test db`). If Docker is
  unavailable, the plan records the gap rather than claiming the check.
- **Telemetry:** the analytics payload snapshot and the crash-report setup pass without edits
  (A18).
- **E2E gate ([`test-deck-app`](../../.claude/skills/test-deck-app/SKILL.md)):** walk these
  steps against a stub auth server:
  1. "No account" shows;
  2. open Account;
  3. start sign-in, with `openExternal` intercepted;
  4. simulate the callback;
  5. the signed-in label shows;
  6. sign out;
  7. "No account" shows again.
- **Owner check, not a gate:** before release, one real Google sign-in against the live project
  on macOS.

## Expected forks (authorized by approving this spec)

- **New runtime dependency:** `@supabase/supabase-js` (D2).
- **New main-process persistence and network calls:** `account.json` and the account service.
  These are not a PTY, window, tab or layout seam.

**Not forks:** no URL scheme, and no change to electron-builder, the updater, signing or the
version.

**Still stops the run:** a gallery specimen that needs a new DL token or invariant change.

## Out of scope

- Settings sync, feedback attribution, and merging the landing's Google sign-in into Supabase
  Auth.
- Billing, Stripe, features gated by tier, and changing a plan from the app.
- In-app account deletion. A future iOS app must offer it (App Store guideline 5.1.1(v)), and
  that needs a Worker route holding the service-role key.
- Other providers, such as GitHub or email.
- The mobile app itself. This spec only keeps the account model client-agnostic.

## Owner actions before launch

- **Google Cloud:** take the Deck OAuth web client, either the one created for feedback or a new
  Deck-only one.
  - Add the authorized redirect URI `https://calkpkscykzmvyayfxih.supabase.co/auth/v1/callback`.
  - Create a client secret.
  - On the consent screen, set the app name to "SpaceVibe Deck" and request only `openid email
    profile`. These scopes are non-sensitive, so Google does not need to verify the app.
- **Supabase → Authentication → Providers → Google:** enable it and paste the client ID and
  secret.
- **Supabase → Authentication → Providers, everything else:** disable Email and Phone, and
  confirm that anonymous sign-ins are off. Once the key is public, an open Email provider lets
  anyone create accounts through `POST /auth/v1/signup`. Each of those also creates a
  `profiles` row and sends mail through Supabase's rate-limited SMTP.
- **Supabase → Authentication → URL Configuration:** add `http://127.0.0.1:*/auth/callback` to
  Redirect URLs.
  - **Why the wildcard should work:** the allow-list glob treats only `.` and `/` as separators,
    so `*` should match a port.
  - **The plan's first task verifies it.** If it does not match, the plan falls back to a small
    fixed port range.
- **Migration:** run `db push` for the account migration before shipping a build that can sign
  in.

The work spans several sessions, so after approval a local plan goes in

1. the migration and the RLS test;
2. the main account service and IPC;
3. UI specimens, owner eye approval, then wiring;
4. the privacy notice and docs.
